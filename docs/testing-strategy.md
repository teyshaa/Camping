# Стратегія тестування та забезпечення якості (HikeManager)

Цей документ визначає підходи, рівні тестування, інструменти та критерії достатності для забезпечення надійності десктопного застосунку **HikeManager** (C# 12, .NET 8 WinForms, SQLite ADO.NET) у рамках Етапу 7 курсу «Програмна інженерія».

---

## 1. Піраміда тестування

Стратегія тестування проєкту побудована на класичній трьохрівневій піраміді:

1. **Модульні тести (Unit Tests)** — основа піраміди:
   - Швидкі, детерміновані тести, які перевіряють ізольовану логіку بدون залежності від зовнішнього середовища.
   - Покривають математичні розрахунки (`BudgetCalculator`), правила валідації сутностей у шарі `Services/`, обробку помилок та форматування експортованих звітів (`HikeReportExporter`).
2. **Інтеграційні тести (Integration Tests)**:
   - Перевіряють взаємодію компонентів шару доступу до даних (`DataAccess/`) зі справжньою реляційною СКБД SQLite.
   - Працюють з тимчасовими ізольованими базами даних у `Path.GetTempPath()`, перевіряючи схему таблиць, індекси, збереження кирилиці, коректність форматів дат та дію зовнішніх ключів (`ON DELETE CASCADE`, блокування видалення маршрутів).
3. **Ручне тестування інтерфейсу користувача (Manual UI Testing)**:
   - Приймальне та регресійне тестування форм WinForms (`Views/`, `Form1`) за заздалегідь підготовленим чек-лістом (`docs/manual-test-checklist.md`).

```
          /  Ручне UI  \         <- Екрани WinForms, Form1 (Checklist)
         /   тестування \
        /----------------\
       /   Інтеграційні   \       <- DataAccess, реальний SQLite, Foreign Keys
      /       тести        \
     /----------------------\
    /     Модульні тести     \    <- Services, BudgetCalculator, Валідація
   /--------------------------\
```

## 2. Що тестується і чому

| Компонент / Шар | Що саме перевіряється | Чому це критично |
|---|---|---|
| **`Services.BudgetCalculator`** | Формули розрахунку: `TotalBudget`, `CostPerPerson`, нульова кількість учасників, округлення AwayFromZero до 2 знаків, суми за категоріями | Запобігає фатальній помилці `DivideByZeroException` та фінансовим неточностям при розподілі коштів групи. |
| **`Services` (Сервіси сутностей)** | Валідація обов'язкових полів, допустимі складності й категорії, довжина рядків, діапазони тривалості, правила дублікатів спорядження, регулярні вирази телефонів | Захищає ядро системи від внесення невалідних бізнес-даних, повертаючи зрозумілі користувачу повідомлення `ValidationException`. |
| **`Services.HikeReportExporter`** | Генерація текстового звіту, агрегація даних маршруту, учасників, спорядження та фінансів | Гарантує повноту та коректність друкованого підсумку походу. |
| **`DataAccess.DatabaseInitializer`** | Створення всіх 5 таблиць (`ROUTES`, `HIKES`, `PARTICIPANTS`, `EQUIPMENT_ITEMS`, `EXPENSES`), індексів та міграцій | Гарантує працездатність БД «з нуля» на чистому комп'ютері користувача. |
| **`DataAccess` (Репозиторії)** | Повний життєвий цикл CRUD, відповідність типів даних, параметризація проти SQL Injection, формати дат `yyyy-MM-dd` | Унеможливлює пошкодження даних та збої через локалізацію чи SQL-ін'єкції. |
| **Цілісність зв'язків SQLite** | Робота `PRAGMA foreign_keys = ON;`, каскадне видалення записів походу, заборона видалення використовуваних маршрутів | Запобігає появі записів-сиріт у таблицях учасників, спорядження та фінансів. |

---

## 3. Що автоматично НЕ тестується (і чому)

Автоматизованому тестуванню **не підлягають форми та користувацькі елементи WinForms** (`Views/*View.cs`, `Views/*EditForm.cs`, `Form1.cs`).

**Причини такого рішення:**
1. Фреймворки автоматизації десктопного UI у Windows (FlaUI, WinAppDriver) вимагають окремого середовища Windows Desktop Session, активного робочого столу, підвищених прав доступу і часто є нестабільними («flaky») при запуску в CI/CD контейнерах.
2. Вся суттєва логіка WinForms винесена в сервіси: представлення лише збирають вхідні значення та відображають результат.
3. Для перевірки працездатності UI створено детальний чек-лист ручного тестування: [`docs/manual-test-checklist.md`](manual-test-checklist.md).

## 4. Інструменти та тестова інфраструктура

- **Тестовий фреймворк:** `xUnit` 2.5+ — лаконічний, сучасний стандарт для .NET із чітким життєвим циклом тестів.
- **Збір покриття:** `coverlet.collector` — збирає Cobertura XML без потреби встановлення глобальних утиліт.
- **Підхід до ізоляції БД (`SqliteTestDatabase`):**
  - Кожен тестовий клас/метод, що тестує БД, створює власний тимчасовий файл `hikemanager_test_{Guid}.db` у системній папці `Path.GetTempPath()`.
  - У методі `Dispose()` обов'язково викликається `SQLiteConnection.ClearAllPools()`, оскільки Windows тримає блокування файлу через пул з'єднань, після чого тимчасовий файл безслідно видаляється.
  - Атрибут `[assembly: CollectionBehavior(DisableTestParallelization = true)]` запобігає конфліктам між потоками за статичний рядок підключення.
- **Фабрика тестових даних (`TestDataFactory`):** створює коректні за замовчуванням екземпляри сутностей для уникнення дублювання рутинного коду (DRY).
- **Ізоляція залежностей:** замість важких сторонніх мок-бібліотек реалізовано рефакторинг сервісів із впровадженням залежностей через конструктори (Constructor Injection).

---

## 5. Критерії достатності тестування

1. **100% покриття** формул розрахунку бюджету та критичних граничних ситуацій (ділення на 0, великі числа, округлення).
2. **Понад 80% покриття коду** (Line Coverage) для шарів `Services` та `DataAccess`.
3. **0 невдалих тестів (Failed: 0)** при будь-якому запуску набоїв тестів.
4. **Детермінованість:** тести не залежать від поточної дати `DateTime.Now`, часового поясу чи регіональних налаштувань операційної системи (використання `CultureInfo.InvariantCulture`).
5. **14+ верифікованих крайових ситуацій (Edge Cases)**, задокументованих відповідними тестами з атрибутом `[Trait("Category", "EdgeCase")]`.

---

## 6. Інструкція із запуску тестів

### Запуск усіх тестів:
```powershell
dotnet test HikeManager.Tests/HikeManager.Tests.csproj
```

### Запуск тестів зі збором покриття коду (Code Coverage):
```powershell
dotnet test HikeManager.Tests/HikeManager.Tests.csproj --collect:"XPlat Code Coverage"
```

### Запуск виключно крайових ситуацій (Edge Cases):
```powershell
dotnet test HikeManager.Tests/HikeManager.Tests.csproj --filter "Category=EdgeCase"
```
